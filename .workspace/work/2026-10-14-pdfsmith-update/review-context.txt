Additional source observations, not runtime proof
available_backends() scans DEFAULT_PREFERENCE rather than all 19 registry entries.
Several installation hints use backend names that do not match extras (aws, azure,
google), and PyMuPDF4LLM's light-extra hint does not install its own package.
Inherited common/preset mappings exceed several backend constructor contracts.
Docling stores some settings without applying them to its converter. Frontier
constructors accept arbitrary kwargs without using them. Their parse paths ignore
provider truncation/finish status. OpenAI's upload cleanup is only on success.
Google batch code concatenates sorted object names without checking per-document
operation metadata; Databricks does not poll a pending statement to completion.
The inventory names per-backend verification and disposition work. These source
findings must get actual producing-code regressions before their repairs close.

LlamaIndex update checked against primary sources
ParseBench was announced April 13, 2026. It evaluates tables, charts, content
faithfulness, semantic formatting and visual grounding and publishes code/data.
Those are LlamaIndex's benchmark dimensions, not PDFsmith measurements. PDF-Bench
owns any corpus/metric reuse and experiments. PDFsmith must preserve usable output
and expose its actual configuration without promising a score or universal quality.
Source: https://www.llamaindex.ai/blog/parsebench

The current LlamaParse getting-started guide uses llama-cloud>=2.8 and Parse v2.
Its migration guide requires tier/version, nests processing/output options and
changes page selection to 1-based indexing; v1 remains available but new features
are v2-only. This affects compatibility and request identity. Our current wrapper
imports llama_parse.LlamaParse and accepts parsing_mode without forwarding it.
The plan proposes a v2 migration under the same backend name, explicit legacy
setting treatment and actual SDK transport checks before any live run.

Consumer contract
PDF-Bench's current reconstruction spec requires pypdf/pdfplumber first, exact
parser/package/source identities, controlled options and separate failed/empty
outcomes. Its current adapter gets BACKEND_REGISTRY[name].loader(), constructs with
kwargs and calls backend.parse(path), so API-only fixes would not repair all of
its behavior. Preserve the direct constructor path or supply a reviewed migration;
do not modify PDF-Bench here. Its cache keys/reference/denominator work belongs to
its owner and is not repaired by a PDFsmith version change.
